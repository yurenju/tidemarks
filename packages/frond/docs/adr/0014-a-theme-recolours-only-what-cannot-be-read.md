# 主題只改讀不到的顏色

讀者設了主題之後，frond **不再把書的每一個 `color` 都換成讀者的墨色**。它逐一看書宣告的顏色，
只換掉在讀者的背景上讀不到的那些，讀得到的原樣留著。

這推翻的是 `settings.ts` 裡曾經寫著的一句話：「設了主題就是放棄書自己的配色，那是 theming 本身的
代價」。那句話當時是誠實的，因為沒有人量過那個代價有多大。

## 舊做法與它的代價

舊做法是一行 CSS：

```css
:root, :root * { color: <前景色> !important; }
```

它要解的問題是真的：書寫死 `color: #000`，深色模式就失效，那是 ADR-0003 實例表上白紙黑字的一列，
也是 user story 43。一行解決，而且沒有例外。

代價量得出來。34 本流通中的書，951 次 `color` 宣告（[量測](../../../../docs/specs/dark-theme-book-colors/measurements.md)）：

| 對比（對 `#1b1b1e`） | 次數 |
| --- | --- |
| 4.5 以上，也就是本來就讀得到 | 190 |
| 4.5 以下 | 708 |
| frond 讀不懂那個值 | 53 |

那 190 次是書拿來分章名、分小標、分圖說的顏色，在深色底上完全讀得到，而舊做法把它們全部抹平。
把「讀不到」修好的同一行，順手把「讀得到」也修掉了。

## 規則

拿到主題時，書宣告的每一個 `color` 值走一次這個順序：

1. **讀不懂那個值** → 不動（`inherit`、`transparent`、`currentColor`、`var(--x)`、`oklch()`）。
2. **對比 ≥ 4.5** → 不動。
3. **沒有色相而且很暗**（chroma < 0.15 且 HSL 亮度 < 0.25）→ 換成讀者的墨色。
4. **其餘** → 保留色相與飽和度，亮度調到剛好過門檻。

半透明的值先跟讀者的背景合成再判定，因為那才是讀者真的看到的顏色。

### 為什麼門檻是 4.5 而不是 3

4.5 是 WCAG 對內文的標準，3 是對大字與圖形元件的標準。**frond 分不出一段字是標題還是內文**，
CSS 上沒有這個資訊，`<h1>` 也不保證比 `<p>` 大。分不出來的時候用嚴的那一個。

這不是沒有代價的選擇：兩個門檻之間有 119 次宣告，訂 4.5 表示這 119 次會被動到。它們大多是書拿來
當標題的暖色（`#a16a2b`、`#c83f21` 這一類）與純紅，動到之後色相一格不差，只有亮度變了。拿「標題
的顏色亮了一階」換「內文的顏色一定讀得到」，在一個閱讀 app 裡是划算的。

### 為什麼沒有色相的顏色要分成兩類

這是規則裡唯一一個看起來像特例的地方，而它是量出來的。中性色照 HSL 亮度排開，樣本裡有一個空隙：

| 亮度 | 有沒有值 |
| --- | --- |
| 0.000 到 0.225 | 361 次宣告 |
| 0.225 到 0.290 | **一個都沒有** |
| 0.290 以上 | 87 次宣告 |

空隙兩邊是兩件不同的事。左邊是書的**內文墨色**，黑、`#333`、`#231815`，讀者的主題本來就是來接手
它的，換成讀者的墨色才對。右邊是書**刻意調淡一階**的灰，圖說、註解、頁碼，那個「比內文淡」是資訊。

所以近黑的換成讀者的墨色，其餘的灰跟有色相的走同一條路：提亮到剛好過門檻，提完仍然比讀者的墨色暗，
「比內文淡」這件事就還在。界線放在 0.25，也就是空隙的中間，樣本裡沒有任何一個值貼著它。

代價是那裡有一個**階梯**：`#373c38`（亮度 0.225）變成讀者的墨色，對比 11.9；`#474a4d`（亮度
0.290）變成一個對比剛好 4.5 的灰。兩個看起來差不多的顏色，結果差很多。接受它是因為量到的分佈說
沒有書落在那一段，而不是因為它不存在。

### 為什麼是提亮而不是換成墨色

換成墨色會把「這裡是強調」抹掉。版控裡的 kusamakura fixture 就是例子：它拿 `#0000FF` 畫傍点、
英文名與縦中横，對比 2.00，讀不到。換成墨色的話那些字跟內文一模一樣，讀者從「看不見」換到
「看不出差別」。提亮之後它還是藍的。

提到**剛好**過門檻而不是提到某個固定亮度，理由是動最少：`#ff0000` 的對比是 4.30，只差一點點，提完
是 `#ff2222`，跟書寫的分不出來；固定亮度會為了那 0.2 把它拉走一大段。

代價要講清楚：**被決定的那一項正是亮度**，所以兩個只差在深淺、而且都沒過門檻的顏色，提完會變成
同一個。書的 `#000080` 與 `#0000ff` 會落在同一個藍上。留下來的是色相與飽和度，以及所有本來就讀得到
的顏色一個都沒動。

### 讀不懂就不動

`transparent` 尤其要不動，書拿它藏字的時候換成墨色等於把藏起來的字挖出來。`var(--x)` 要展開就得在
frond 裡跑一套自訂屬性的 cascade，那是猜。代價記在量測裡：34 本裡 35 次宣告因此不會被處理。

### 讀者的背景色讀不懂的時候，退回舊做法

整套規則的每一步都要跟讀者的背景算對比。`theme.background` 如果是 frond 認不得的寫法（消費端哪天
改用 `oklch()`），就沒有東西可以算，這時候退回 `:root, :root *` 那一行。這是安全的那一邊：寧可抹平
也不要讓黑字留在黑底上。

## Consequences

**清單上多一項，`reader-stylesheet` 那一項的內容也改了。** 新的是 `theme-colors`，理由是
`reader-blocked`、`onlyWhenReaderOverrides: true`：沒有主題就一個字元都不改寫。`reader-stylesheet`
從「把 `color` 寫到每一個元素上」變成「只寫到根元素上」，那是同一項介入變小，不是新增一項。

**這是清單裡第二項會改變書宣告的值的介入**（第一項是 `relativise-font-size`）。它跟第一項的形狀
一樣：保留可以保留的那一半（色相、飽和度、以及顏色之間的高低），放棄擋著讀者的那一半（絕對亮度）。

**背景色沒有跟著改。** 書用底色區分的引文框，深色模式下仍然是 `transparent`。那是另一個問題：
底色要「跟著變深」而不是「變透明」的話，還要決定深淺的對應關係。這一輪不做。

**淺色模式一個字都沒變**，因為當時 Tidemarks 的淺色模式根本不給主題
（`packages/app/src/lib/settings.ts`）。哪天淺色也給主題，同一套規則就會生效，那時候要重新
看一次門檻。

> 生效了。⚠️ 門檻**沒有跟著補**——上面那兩個數字是 34 本書量出來的，亮端沒有對應的量測，補一個
> 憑感覺的常數會讓這份 ADR 從量測變成一半量測。實際的後果是：一本把內文設成白字的書，在淺色

> 跟旁邊沒宣告顏色的段落不同色。哪天手上有那樣一本書，就是補這個門檻的時候。
