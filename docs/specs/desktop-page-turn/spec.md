# 頁鈕與方向鍵翻頁：看得見那一頁走掉

狀態：已實作。對齊與實作日期 2026-08-14。基準：`main`（`packages/app/src/components/Reader.tsx`、
`packages/app/src/lib/navigator.ts`）。

這份文件是**決定**，不是提案。它接在
[docs/specs/swipe-to-turn/spec.md](../swipe-to-turn/spec.md) 後面，改的是那一份〈動畫〉那一節的
後半句；[ADR-0024](../../adr/0024-turning-a-page-is-a-swipe-and-nothing-else.md) 的分工（手指只有
拖曳、桌機走頁鈕與方向鍵）一個字都不動。

## 根因

拖曳翻頁上線之後，兩種輸入的落差變成一個病。

手指翻頁看得到整件事：頁面跟著手指走，鄰頁從側邊露出來，是往前還是往後**由畫面自己說**。頁鈕與
方向鍵沒有這一段，舊的那一頁在兩幀之間被新的換掉，中間什麼都沒有。

而**同一本書的兩頁長得很像**：同一個字體、同一個字級、同一組留白，滿版的中文更是如此。一次瞬間
切換之後，讀者手上唯一的證據是「畫面變了」，那既可以是往前一頁也可以是往後一頁，也可以是自己按
了兩下。往前按一下、發現不對想退回去的時候最明顯：兩次操作在畫面上是同一個事件。

順帶一個更小但一樣真的：**按到書尾的頁鈕什麼事都不會發生**。「到底了」與「這顆鈕壞了」在畫面上
分不出來，這正是拖曳那邊已經用阻尼回彈答過一次的題。

## 讀者看到什麼

按頁鈕或按方向鍵，**當前頁滑走、下一頁跟著滑進來**，跟拖曳放手之後那一段是同一個動作，只是從頭
播到尾。往前與往後的滑動方向相反，所以方向是看得出來的。

書首書尾按下去：頁面往外挪一小段再彈回來，露出來的是紙色的底。

`prefers-reduced-motion: reduce` 時全部瞬間落位，包含那個回彈（挪出去與挪回來在同一時間發生，等於
沒有動）。

## 規則

### 誰有動畫

| 路徑 | 動畫 |
| --- | --- |
| 拖曳放手（翻過去／回彈） | 有，本來就有 |
| **頁鈕** | **有，這一輪加的** |
| **方向鍵** | **有，這一輪加的** |
| 目錄跳頁、筆記跳頁、定位軸 | **沒有，維持瞬間切換** |
| tap | 不翻頁（ADR-0024） |

**跳頁不給動畫，是因為它不是翻頁。** 目錄跳到第七章、定位軸拉到 60%，滑一頁的距離不代表跨過去
的距離，那個動畫會是一句假話。它們要的回饋是「到了」，不是「往哪邊」。

**沒有按裝置分。** 這條規則問的是輸入是什麼，不是機器是什麼：觸控裝置接了鍵盤，方向鍵一樣有動畫；
桌機的視窗夠寬所以看得到頁鈕，那也只是 CSS 的事。按裝置分岔就是同一段程式碼要維護兩種行為，而
沒有人說得出那兩種各自的理由。

### 鄰頁從哪一邊進來

拖曳時這件事**不看書的方向**：頁面跟著手指走，所以新的那一頁從手指離開的那一側進來。按鈕沒有手指，
所以只剩書的方向可以問：右開本的下一頁從左邊進來，上一頁從右邊進來。

兩條路徑算出來的邊必須一致（同一本書、同一個方向，用手翻跟用按鈕翻不能從不同邊滑進來），這件事
由 `navigator.test.ts` 的一條測試釘著。

### 時間與緩動

| | 時間 | 緩動 | 為什麼 |
| --- | --- | --- | --- |
| 拖曳收尾 | 180ms | ease-out | 讀者已經移了大半，這只是尾巴，起頭要接上手指離開時的速度 |
| **按鈕／方向鍵** | **220ms** | **ease-in-out** | 從靜止跨過整個畫面，兩頭都得從靜止開始 |
| **書首書尾回彈** | **110ms × 2** | ease-out | 一小段出去再回來 |

220ms 是**挑的，不是量的**。上限來自讀者一本書要翻幾千次，每一次都得等它；下限來自它得看得出來是
一個移動而不是一次閃爍。要調的話跟 measurements.md 一起看。

回彈的幅度是一整頁的 **6%**，同樣是挑的。它跟拖曳的阻尼上限（25%）不同數字是刻意的：那個是讀者
自己推出去的距離，這個是系統替他推的。

### 連按

快速連點方向鍵時，兩次按鍵之間可能比一次翻頁短。**新的一次按鍵會把上一次直接送到終點再開始**，所以
連點 N 下就是翻 N 頁，只是中間幾頁一閃而過。

**按住不放是另一回事：它只翻一頁。** 翻頁掛在 `keyup`，而瀏覽器的 auto-repeat 只重複發 `keydown`，
放開時才發一次 `keyup`。這一段以前寫成「按住方向鍵不放時鍵盤的重複速度比一次翻頁快」，跟程式碼對不
上。要不要改成按住就連翻是產品決定，還沒有人決定過（measurements.md §3）。

不這樣做的話會壞得很難看：frond 的 `beginTurn()` 會取消掉進行中的那一次翻頁，所以每一次重複都開一
個新的、都沒有完成，按住方向鍵，書一動也不動。

### 鄰頁還沒排好的時候

frond 的相鄰頁面是背景排的，開書後與改排版後有一小段窗口是空的（`TurnInProgress.hasPreview` 為
false）。那段時間滑過去會是「頁面移開，後面什麼都沒有」，所以**這一次退回瞬間切換**：讀者拿到他要
的那一頁，只是沒看到它進來。這跟 frond 的 `commit()` 在同樣情況下做的取捨一樣。

## 分工

沿用 swipe-to-turn spec 的那張表，這一輪只多兩格。

| | 誰 |
| --- | --- |
| 進行中的翻頁：開始、位移、commit、cancel | frond（本來就有，這裡只是換一個東西驅動它） |
| 鄰頁從哪一邊進來（`edgeFor`） | app（`navigator.ts`，跟 `dragTowards` 並排） |
| 動畫的時間與緩動、連按怎麼接、沒有鄰頁時怎麼退 | app（`Reader.tsx`） |

**frond 一個字都沒改。** 這是這個做法最值得說的一點：拖曳翻頁已經把「翻到一半的那一頁」變成 frond
的狀態（frond [ADR-0013](../../../packages/frond/docs/adr/0013-a-half-turned-page-is-frond-s-state.md)），
而那個狀態不在乎是誰在推它：手指推是拖曳，`requestAnimationFrame` 推就是這一份 spec。

## 不在這一輪

- **翻頁的視覺效果仍然只有平移。** 不做翻書、捲曲、淡入。
- **桌機的滑鼠拖曳。** 滑鼠拖曳是選字，這條沒有變。
- **動畫時間做成設定。** 開關的成本是每一條翻頁路徑從此有兩種行為要測（ADR-0024 已經論過一次）。
- **螢光層跟著頁面一起走。** 翻頁動畫期間畫在上層的螢光框停在原地，等 `relocate` 之後才重算。這是
  拖曳翻頁本來就有的行為，兩條路徑一致，要修是另一件事（見 measurements.md 第 2 項）。
