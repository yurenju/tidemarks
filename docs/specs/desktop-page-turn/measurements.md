# 頁鈕與方向鍵翻頁：要量的數字

[spec.md](spec.md) 裡寫死的數字，來源都在這裡。**沒量過的就寫「猜的」**，不要讓一個猜測看起來像
一個結論。

## 1. 220ms 是不是對的

**猜的。** 形狀是有理由的（要比 180ms 的收尾長，因為那一段只走剩下的距離，這一段走一整頁），數字
沒有來源。

它兩頭都有壓力，所以只調一個方向不會有答案：

- **太長** → 一本書幾千次翻頁，每一次都在等它。症狀是連續翻頁的時候覺得書變重了。
- **太短** → 看不出來是一個移動，跟瞬間切換沒有差別，那這一整份 spec 就白做了。

**怎麼量**：連續讀 10 分鐘，只用頁鈕或方向鍵，記兩件事。

- **等**：有沒有出現「我已經想看下一頁了，它還在動」。每 50 次翻頁超過 5 次就往下調。
- **看不到**：翻完之後說不出剛才是往前還是往後。出現任何一次就往上調。

兩邊同時超標代表**單靠時間不夠**，那才是動緩動曲線（現在是 ease-in-out）的訊號，而不是繼續在
220 附近挪。

先在 chromium 上量，再看 firefox。這一段是純 `requestAnimationFrame` 加 `transform`，
`turn-pacing.spec.ts` 已經證明過那條路徑在容器裡不掉幀，所以引擎差異的優先度低於上面那兩欄。

## 2. 螢光層在翻頁期間不會跟著走

**已知，未修，未量。** 螢光框畫在 `HighlightLayer`，那一層在 frond 的容器**外面**，而翻頁移動的
是容器裡的兩個 frame。所以翻頁動畫期間，螢光停在原地、頁面從它底下滑過去，等 `relocate` 之後才
重算（`geometry` 那個 tick）。

**這不是這一輪帶進來的**：拖曳翻頁一樣如此，兩條路徑的行為一致。這一輪只是讓它在桌機上也看得到。

**怎麼量**：開一本畫過重點的書，停在有螢光的那一頁，按頁鈕，錄影逐幀看螢光框有沒有跟著頁面走。
容器裡量得到，不需要真機。

**若要修**：兩條路。把螢光畫進 frond 的 frame 裡（那會讓 frond 碰到 UI 政策，ADR-0002 擋著），或者
讓 app 在翻頁期間把螢光層跟著 `moveTo` 的距離一起平移（`TurnInProgress` 已經把距離交出來了，所以
這條不需要 frond 補任何事實）。**後者才是這個 repo 的答案**，但它要處理「翻過去之後螢光是下一頁
的」這件事，所以不是兩行。

## 3. 連按會不會漏頁

**未量。** 這一節本來寫的是「按住方向鍵不放」，那是錯的，先更正。

**按住方向鍵不會連續翻頁。** 翻頁掛在 `keyup`（`Reader.tsx` 的 `onKeyUp`，以及交給 frond 的那個
同名 handler），而瀏覽器的 auto-repeat 只重複發 `keydown`，放開時才發一次 `keyup`。所以按住三秒
再放開，翻的是一頁。

會走到 `landCommand()` 的是**快速連點**：兩次按鍵之間比 220ms 短的時候，新的一次會把上一次直接送
到終點再開始。spec〈連按〉那一段講的是這件事，只是把觸發條件寫成了按住。

要不要改成 `keydown` 是另一個問題，這份文件不回答。按住不翻頁對讀者來說不見得是錯的（多數閱讀器
會連翻），但那是產品決定，不是量測結果。

**怎麼量**：快速連點右方向鍵十下，數畫面翻了幾頁（把 `fraction` 記下來比數畫面可靠）。原生的連點
速度在測試裡派得出來，但**人手真正的連點節奏**派不出來，所以這一項還是要真人做。

**若會漏**：那就是 `landCommand()` 把上一次送到終點之後，frond 的 `refreshNeighbours()` 還來不及
把下一個鄰頁指好，於是下一次按鍵走了「沒有鄰頁就瞬間切換」那條退路。退路本身是對的（讀者還是拿到
了那一頁），要判的是連按時它出現的頻率高到會讓動畫閃爍。

## 4. 方向鍵翻頁的重繪與幀距

**已量。** 量測在 `packages/app/tests/browser/reader/turn-pacing.spec.ts`，跟拖曳翻頁那一組並排，
共用 `tests/browser/support/pacing.ts`。

每一種翻頁都切成兩段量，因為兩段壞掉的原因不一樣：

| 路徑 | 前半 | 後半 | 界線 |
| --- | --- | --- | --- |
| 拖曳 | `follow`（頁面跟著手指） | `settle`（放手之後的收尾與 commit） | `pointerup` |
| 方向鍵 | `slide`（220ms 的緩動） | `reshuffle`（commit 與 frond 重指鄰頁） | 送出 `keyup` 起算 `TURN_COMMAND_MS` |

### 幀距

十二次方向鍵翻頁，丟掉暖機那一次。三家瀏覽器都在容器裡跑，`fullyParallel`：

| 引擎 | 一幀 | slide 掉幀 | reshuffle 掉幀 |
| --- | --- | --- | --- |
| chromium | 16.7ms | 0/158 | 0/288 |
| firefox | 17.1ms | 0/157 | 0/295 |
| webkit | 16ms | 0/168 | 4/299（1%） |

拖曳那一組在同一次執行裡是 follow 0/138 三家皆同，settle 最差 webkit 的 2/144。

**所以 220ms 那段動畫在容器裡一幀都不掉。** 這不代表手機上也不掉：這裡數的是
`requestAnimationFrame` 的 callback，也就是瀏覽器**開始**畫一幀的時刻，不是合成器把它送上螢幕的
時刻。手機的瓶頸在後者，那一段只有真機量得到（swipe-to-turn/measurements.md §3）。

### 重繪

只有 chromium 量得到（trace 類別是它獨有的）。單位是「一次翻頁幾個 `Paint`」，**暖機那一次與翻頁
之間的空檔都不計入**：

| | 有 compositor layer | 拿掉 layer |
| --- | --- | --- |
| 拖曳 | 4（follow 4、settle 0） | **22**（follow 22、settle 0） |
| 方向鍵 | 2（slide 0、reshuffle 2） | **2**，沒有變 |

「拿掉 layer」是把 `section-view.ts` 的 `promote()` 改成不設 `will-change` 再量一次，量完就還原，
沒有 commit 進去。

兩件事值得記下來：

**方向鍵那 220ms 幾乎不重繪。** `slide` 是 0。單獨驗過那段動畫真的在跑：逐幀讀 page frame 的
`transform`，十四幀從 0 一路走到 -888px，然後 commit 把它歸零，所以這不是走了
`commandTurn()` 那條「沒有鄰頁就瞬間切換」的退路。十四幀的移動、零次重繪，代表頁面純粹靠
compositor 搬 layer。

**「0」要扣一格看。** 界線那一幀的標記是在該幀的 `requestAnimationFrame` callback 裡下的，而一幀
是先跑完 callback 才畫，所以**動畫最後一幀的重繪一定被算進 `reshuffle`**，`slide` 結構上就拿不到
它。真正的說法是「那段動畫至多重繪一次，而那一次記在後半段」。

**但方向鍵這條路對「拿掉 layer」不敏感。** 同一個回歸讓拖曳從 4 變成 22，方向鍵卻還是 2。所以
`COMMAND_PAINTS_PER_TURN_CEILING` **沒有一個量到的壞端可以夾**，它是 8，理由來自失敗的算術而不是
量測：slide 是 220ms，60Hz 下大約十三幀，一個開始逐幀重繪整頁的翻頁不可能低於十三，8 壓在量到的
2 之上、十三之下。拖曳那條（10）兩端都是量到的。

拖曳的上下限跟這份文件以前寫的 8.6／42.6 不同，是因為計數方式換了：那一組把整段 trace 的
`Paint` 除以全部七次翻頁（含暖機），現在是只算翻頁窗口內、且排除暖機。同一個現象，兩個尺度。

### 沒量到的：這些翻頁有沒有跨 section

**未驗。** 跨 section 的翻頁比同一節內貴得多，所以量測理應留在同一節裡，而現在守著這件事的只有一
句註解（「七次前進還在第一節內」），方向鍵這一組要十三次。

試過讓它可驗，失敗了：page frame 的 `src` 是那個 frame 自己的 blob URL，不是 section 的身分，
frond 三個 frame 輪替的時候它就變了，而 frond 沒有把 section 放進 DOM 的任何地方。

**要驗就得讓 frond 說出一個 frame 指的是哪一節**，那正是 CLAUDE.md〈frond 的邊界〉說的「拿不到只
有 frond 知道的事實，就讓 frond 補上那個事實」。那是另一輪的事，不在這一輪。
