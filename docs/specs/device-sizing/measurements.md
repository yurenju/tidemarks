Chromium（`playwright-cli`，host 上量的），亮色，兩本書、兩條畫線，其中一條是中文。

| 寬度 | `.library` 實寬 | 引文可用寬 | 牆封面 | 牆欄數 | 正在讀那一排 |
| --- | --- | --- | --- | --- | --- |
| 390 | 375（跟著視窗） | 308 | 109 | 3 | 46.8 |
| 600 | 585（跟著視窗） | 518 | 126 | 4 | 46.8 |
| 820 | **736（封頂）** | **640** | 122 | 5 | 46.8 |
| 1280 | **736** | **640** | 122 | 5 | 46.8 |
| 2560 | **736** | **640** | 122 | 5 | 46.8 |

**736 是怎麼來的。** 封頂的依據是「引文剛好放得下 40 個字」，不是一個好看的數字：

```
640  引文 40em × 16px（--type-body，fine）
+ 32  卡片左右內距（--space-4 × 2）
+  3  卡片左緣那條墨線
+ 60  頁面左右邊距（--space-6 × 2，820 以上）
= 735，取 736
```

820 那一格量到 `.library` 左緣 34.5、引文左緣 83.5，差 49 = 30 + 16 + 3，跟推導對得起來；右側多
出來的 1px 是取整留的餘裕。**引文從 820 起就一直是 640**，也就是 40em，窗再寬都不動，那正是封頂
的意思，也是為什麼 1280 那條 media query 可以整段刪掉。

拉丁文的書換另一格：`detectScript()` 判成 `latin` 的時候引文停在 30em（480px），卡片與頁面邊距
不變，所以它用不完那 736，靠左排在同一條邊界上。

### 三家一起量的那幾格

同一串操作在 host 上跑過 chromium／firefox／webkit（`playwright-cli`，手機那一欄用
`--device "iPhone 15"`）。

| | 桌機 1280／2560（fine） | iPhone 15（coarse） |
| --- | --- | --- |
| `.library` 實寬 | 736 | 393（跟著視窗） |
| 左右留白 | 264.5／904.5，兩側**相同** | 0 |
| 引文 `max-width` | 640px = **40em** | 680px = **40em** |
| 正在讀那一排 | 46.8 | **48.6** |
| 〈Keep reading〉 | 46.8 | **48.6** |
| 回訪卡的 ‹ › | 38.8–40.4 | **44** |
| 牆封面／欄數 | 122.4／5 | 115／3 |

**三家的差異只有一格**：‹ › 在 webkit 是 38.8、另外兩家 40.4，那是字符寬度不是規則。其餘每一格
三家完全相同。

兩件這張表講出來的事：

- **引文兩邊都是 40em，px 不同**。桌機 `--type-body` 16px、手機 17px，所以 640 對 680，ceiling
  是用 em 定的（ADR-0012），量出來就會是這個樣子。**寫成 px 抄進樣式的話這一格會壞掉，而且不會有
  東西紅。**
- **排的高度與觸控目標分頭走。** 46.8 → 48.6 那 1.8px 不是版面規則做的，是 `--tap-min` 從 32 變
  成 44 之後 `.reading-now .primary` 跟著長高，把整排撐開的。‹ › 那一列更直接：38.8 → 44。
  這正是 ADR-0023 說的兩件事：**排是寬度的事，鈕是手的事**，這裡剛好兩邊都過。

（`.reading-now` 的 `getBoundingClientRect()` 量到 68.8／76.8，那是連著上緣 22／30 的間距一起算
的；表上寫的是扣掉 `padding-top` 之後那一排自己的高度。）

**進度那兩行在 600 以下不出現在排上。** 390 上四樣東西擠一列的結果是書名被壓成 0、`⋯` 掉出右
緣。讓掉的是四樣裡最不重要的一樣，而且沒有真的消失，同一本書的卡片就在牆的第一格，兩行都在
那裡。

**牆的欄數與封面寬**是 `auto-fill` 的輸出：820 起固定 5 欄、封面 122px，因為容器不再變寬了。
以前 820 是 6 欄、1680 是 9 欄，那是容器跟著視窗長的結果。

三件跟設計稿對不上的事：

1. **體積比 2:1 在 820 以下不成立**（1.47 與 1.53）。設計稿自己的手機數字也一樣（132 對 ~114 是
   1.34），所以那條不變式實際上是**820 以上**的規則。窄的時候大書靠的是位置：自己一列、有書名、
   帶著整屏唯一的動作。第一版用設計稿的 `16vw` 更糟：600 與 820 兩格都貼在 clamp 下限 132px，
   對到 126px 的牆封面，比值 1.09。改成 `26vw` 才把 820 那格拉起來。
2. **欄數比設計稿多**（820 是 6 不是 5，1680 是 9 不是 6–7）。欄數是 `auto-fill` 的結果，不是輸入；
   設計稿的數字來自它自己的 padding 與 gap。封面寬度維持在 109–132 這個帶子裡，「加欄不放大」這條
   成立。
3. **`auto-fill` 是用軌道的上限算欄數的**，所以 `minmax(112px, 132px)` 在 390 只排得出 2 欄
   （3×132 已經超過可用寬度）。上限改成 `1fr`、132px 移到 `.book-card` 的 `max-width`，才拿得到
   設計稿要的 3 欄。

〈繼續讀〉：高 50.9px（≥48 ✓），但**寬度是資訊欄的寬（390 上是 94px），不是整屏**。設計稿寫「拉滿
寬」，那要把動作列從資訊欄移出去成為第三個 grid 區域；沒做，記在這裡。

第 3 點還算數（`auto-fill` 的規則沒變）；1、2 兩點量的是已經不存在的元件。

## Playwright 的裝置模擬到不到得了 CSS

會。這決定了手機那一半守不守得住：

| 引擎 | `pointer: coarse` | `any-pointer: coarse` | `hover: hover` |
| --- | --- | --- | --- |
| chromium（`isMobile`） | true | true | false |
| webkit（`isMobile`） | true | true | false |
| firefox | 沒有 `isMobile` 可用 | — | — |

兩件要知道的事：

- `page.setContent()` 那種沒有 viewport meta 的頁面，`innerWidth` 會是 **980**，寬度斷點量起來就是
  錯的。要打真的 app（`index.html` 有 viewport meta），量到的才是 390。
- **實際守著手機分支的只有 chromium 一家**：firefox 沒有模擬，webkit 在這個映像裡存不進 `Blob`
  到 IndexedDB（見 `storage.spec.ts`），所以連書都匯不進去。`hand-held.spec.ts` 兩家都 skip 掉。

  ⚠️ **這一條講的是容器裡的測試，不是 host 上的截圖。** 2026-08-25 在 host 上用
  `playwright-cli --device "iPhone 15"` 量過，**三家都拿得到 `any-pointer: coarse` 與 393 的
  viewport**，webkit 也匯得進書（host 開 `--persistent`，沒有暫時性 profile 那個問題，見
  `docs/agents/pull-requests.md`）。所以手機那一半在**證據**這一層三家都看得到，在**自動化**
  那一層仍然只有 chromium 守著。
