# 裝置與尺寸

同一個畫面在不同的視窗寬度、不同的指標型別、亮暗兩個模式底下長什麼樣。

> **2026-08-22：底下寫的顏色與陰影已經不算數了。** 視覺方向換成 Indigo Dye，`--accent` 改名
> `--tide`（而且從綠變藍），`--shadow-*` 整組移除，「浮起來」現在由表面階數說。版面、尺寸與
> 行為那幾段不受影響。值的正本在 `packages/app/src/index.css`，規則在
> [docs/design-system.md](../../design-system.md)，理由在
> [ADR-0022](../../adr/0022-the-interface-is-a-print-shop.md)。

畫面上**有什麼**、流程**怎麼走**不在這裡，那是 [ux-replan/spec.md](../ux-replan/spec.md)。
為什麼分成兩種 media query 見 [ADR-0023](../../adr/0023-width-places-things-pointer-sizes-them.md)。
值的正本是 `packages/app/src/index.css` 的 `:root`，這份文件會過期，那個檔案不會。

## 骨架

| 問的是 | 用什麼判斷 |
| --- | --- |
| 東西排在哪裡（一欄還兩欄、bar 在頂還在底） | 視窗寬度 |
| 東西多大（命中區、bar 的位置） | `any-pointer: coarse` |
| 字多大 | `pointer: coarse` |
| 拖曳吸不吸附、位移算不算 tap | 事件型別（`lib/touch.ts`），不是 CSS |

兩個 pointer query 不一樣，是因為它們問的不是同一件事。命中區問「這台機器**有沒有**一根粗指標」，
觸控筆電有，所以它要 44px。字級問「**主要**那根是不是手指」，觸控筆電的主要指標是觸控板，
使用者坐在桌前，字不該變大。

**不嗅 user agent，不用寬度猜手指。**

## 斷點

390 是地板不是斷點，而**上面那一頭是封頂**：書架停在 `.library` 的 `max-width`，過了那個寬度整
個畫面只是被推到中間，沒有一條規則還有話要說。所以寬度的 media query 只有兩條給書架
（600 / 820），加上閱讀器自己那條 1024。

| 寬度 | 常見於 | 書架 | 閱讀器 chrome |
| --- | --- | --- | --- |
| 基準（≥ 390） | 手機直立 | 一欄；牆 3 欄；排上不顯示進度 | 粗指標時底部 bar |
| ≥ 600 | 窄視窗、分割畫面 | 一欄；牆 4 欄；排上補回進度 | 頂部 chrome |
| ≥ 820 | 平板 | 一欄；牆 5 欄；**寬度到頂 736px** | 頂部 chrome ＋左側面板 |
| ≥ 1024 | — | 同上（書架沒有變化） | 面板改成推開，不再蓋住 |
| ≥ 1280 | 桌機 | 同 820 | 同上 |
| ≥ 2560 | 寬桌機 | 同 820，整片置中 | 同上 |

以前這裡有一條 1280 把書架切成兩欄（大書一欄、牆一欄）。**那條刪掉了**：它靠 `.shelf:has(.reading-now)`
觸發，而大書已經不存在，那個選擇器永遠不會命中。

## 書架

第一屏最上面是**回訪卡**：每天挑五條畫線，一次顯示一條，可以滑動或用 ‹ › 翻，兩端就停住。正在讀那
一本在它下面，是一橫排。

> **2026-08-26 改名並換了挑選規則。** 原本叫〈輪詢卡〉、照建立時間由新到舊翻、翻到底繞回第一條；
> 現在照「上次出現在卡片上是什麼時候」排，每天抽五張，高度固定。行為的正本是 `CONTEXT.md`
> 的〈回訪卡〉與〈畫線的隊伍〉。底下的版面規則不受影響，它換的是誰上場，不是它佔多大。
>
> **2026-08-29 上面那一段整段不算數了。** 五則、翻閱、固定高度全部拿掉，改成一天一則、隨機挑、
> 當天固定，卡片高度砍到約三分之一。〈畫線的隊伍〉那一節也隨之刪掉。理由與那條「五」為什麼答不
> 出來，見 [ADR-0038](../../adr/0038-the-revisit-card-is-a-way-in.md)。

**整屏唯一的主要動作，帶在正在讀那一排上。** 這是取代「大書與牆封面的體積差維持 2:1」的那條不變式，
而它換掉的是**看哪裡**：舊的那條用**體積**回答「正在讀那本要怎麼跟其他書不一樣」，新的這條用
**動作**。

會換，是因為舊的那條沒有主詞了，大書不在了，體積比沒有東西可以比。但它背後的問題還在，而且答案
其實那份 spec 自己就寫過：820 以下兩者本來就不在比大小，「大書靠的是位置、書名、和整屏唯一的動作」。
把 820 以下那套推廣到所有寬度，就是現在這一條。用動作而不是用尺寸還多一個好處：**尺寸會被下一次
改版稀釋，動作不會**，只要那顆〈Keep reading〉還是這一屏唯一的主要動作，那一排就還是認得出來的。

**為什麼大書要降級。** 回訪卡放在正在讀那一塊的上面或下面都一樣：兩個大塊在同一欄裡上下緊貼，讀
起來就是「下面那本書的筆記」，即使卡片上寫著別本書的書名。加標籤、加分隔線都蓋不過那個結構訊號。
畫面上只留一個大塊，歧義才會消失。

- **書架封頂 736px，整片置中。** 依據是「引文剛好放得下 40 個字」，推導與量到的數字在
  [measurements.md](measurements.md)。卡片、正在讀那一排、封面牆共用同一條左右邊界。
- **回訪卡的引文用閱讀器那一套行長天花板**（[ADR-0012](../../adr/0012-line-length-has-a-ceiling-measured-in-ems.md)）：
  中日韓 40em、拉丁 30em，屬於哪一類由 `detectScript()` 看書自己的文字算。**那兩個數字不抄進樣式**：
  `lib/line-length.ts` 的 `LINE_LENGTH` export 出來，元件把它寫進 `max-width`。抄過去的數字不會
  在原始值改變的時候壞掉，它只會安靜地繼續算錯的行長。
- **出處跟書名同一個視覺重量**：封面小圖加上加粗的書名，字級 `--type-lede`，比正在讀那一排的書名
  （`--type-body`）大。第一屏上最顯眼的書名必須是這句話的出處，否則句子會被歸給錯的書。
- **正在讀那一排高 46.8px（桌機）／48.6px（粗指標）**，小封面 1.625rem 寬。差的那 1.8px 不是版面
  規則做的，是 `--tap-min` 從 32 變 44 把排撐開的：**排的高度由寬度決定、〈Keep reading〉的大小由
  `--tap-min` 決定**，兩條不能互相代替（[ADR-0023](../../adr/0023-width-places-things-pointer-sizes-them.md)）。
- 封面牆 `repeat(auto-fill, minmax(108px, 1fr))`，132px 的天花板放在 `.book-card` 的 `max-width`。
  **不能寫成 `minmax(108px, 132px)`**：`auto-fill` 是用軌道的**上限**算欄數的，那樣寫在 390 只排得
  出兩欄。**空間變多是加欄，不是放大。**
- **正在讀那本在牆上也看得到**，排在第一格。以前會把它濾掉避免重複，那等於讓〈最近碰過〉多一個沒
  寫下來的例外；而且現在不成問題，那一橫排讀起來是一個動作，不是書櫃裡的一本書。

**欄數是 `auto-fill` 的輸出，不是輸入。** 封頂之後 820 以上固定 5 欄、封面 122px，因為容器不再變寬。

## 閱讀器的 chrome 與面板

底部 bar 只在 `(any-pointer: coarse) and (max-width: 819px)` 出現。其餘一律頂部。

**進度軸永遠留在底部**，兩個分支都是。它講的是「這本書」而不是「這個工具」，而且底緣是它天生
的位置。

頂部是**兩列**：第一列 `‹ 書架`、書名、章節、`⋯`，第二列四個入口（目錄／筆記／排版／設定），項目高
36px。設計稿畫的是一列，把入口跟書名排在同一條上；做成兩列是因為那樣每一塊都還是一個有邊界的盒子，
而併成一列要把外層的 `<header>` 變成 `display: contents`，那會讓它在測試裡量不到，而 `chrome-top`
正是既有測試抓著的東西。設計稿的原型上也沒有回書架那顆。

**面板**（桌機的目錄／筆記／排版）：

- 從左緣進來，寬 236px，`--surface-sunken` 底，右緣 1px `--line-hair`。上下兩緣**不是常數**：面板
  畫在兩條 bar 中間那個框裡（`.chrome-gap`），所以「在入口列以下、進度軸以上」是那個框自己的邊。
  第一版用常數對，量出來差 9px。
- **蓋住內容，不推開。** 推開會改變內文欄寬，frond 會重新分頁，讀者當下那一屏就跳掉了：問「我在
  哪裡」不該把人移走。這也是為什麼〈行長〉那條「沒有下限」不必為了面板破例。
- **不常駐。** 它是〈找〉狀態的一部分，跟三個狀態互斥那條規則（ADR-0020）沒有例外。
- 維持 `modal={false}`：backdrop 蓋書、不蓋底部的 Scrubber，Scrubber 在面板開著的時候照樣拖得動。
- 關法三條：點內文、`Esc`、再按一次同一個入口。點內文那一下收的是**面板**，chrome 留著；再點一下
  才收掉 chrome。兩段而不是一段，是因為三個狀態的機器本來就這樣走（〈找〉開著面板 →〈找〉→〈讀〉），
  為了少一次點擊在中間插一條特例，等於在 ADR-0020 的互斥上開一個洞。
- 手機那邊維持從底部升起的全屏面板，**同一個元件**（`Panel`）。錨在哪一邊由 CSS 決定，不是 prop：
  版面不該等 JavaScript。元件裡只留一件 CSS 決定不了的事：手指往哪個方向撥掉它（`swipeDirection`），
  那件事猜錯一格畫面也不會壞。

## 字級

一律 `rem`，不是 px。理由不是潔癖：`settings.ts` 的 `fontSize` 是根字級的百分比
（[ADR-0006](../../adr/0006-font-size-is-a-percentage-of-the-readers-root.md)），讀者放大瀏覽器
字級的時候書會跟著長，**介面只有寫成 rem 才會跟著長**。寫 px 的結果是書變大、介面顯得更小。

七階的名字不動，值改成 rem，另外在 `@media (pointer: coarse)` 裡 re-declare 其中四階：

| token | 桌機（fine） | 手機（coarse） | 用在 |
| --- | --- | --- | --- |
| `--type-title` | 1.3125rem | 1.3125rem | 現在沒有畫面用它（大書拆掉之後空出來的一階；字標走 `--type-display`） |
| `--type-lede` | 1rem | 1.125rem | 抽屜標題 |
| `--type-body` | 0.9375rem | 1rem | 介面內文、列項 |
| `--type-ui` | 0.84375rem | 0.9375rem | bar 上的字、label |
| `--type-note` | 0.78125rem | 0.875rem | 說明、註腳 |
| `--type-eyebrow` | 0.6875rem | 0.75rem | 小標 |

為什麼手機要大：漢字沒有 x-height，字身塞滿，筆畫間的空隙比拉丁小；宋體的橫筆細，DPR 3 上小字級
靠灰階抗鋸齒會發灰；手持距離近但角度斜，實際角分辨率沒有變好。量的是**字面方框**，不是「幾 px」。

小標在 coarse 下 `letter-spacing` 從 `.16em` 降到 `.14em`：字大了之後同樣的字距讀起來是散，不是
標籤。（設計稿另外說小標的顏色要從 `--text-faint` 提到 `--text-muted`，那件事**已經是真的**，
`--text-faint` 在這個 repo 裡本來就不承載文字。）

**硬規則：小於 1rem 的漢字不用 400 以下的字重，也不用 `--text-faint`。** 需要更淡就換更短的句子。
這是無障礙，不是偏好。

## 暗色的可按性

暗色下色差、邊、影子三個訊號同時變弱，所以規則是：**單獨站著的可按物件一定有一條看得見的邊。**

「單獨站著」是關鍵。`.ghost` 從來不單獨站著，它永遠在一個已經有邊界的容器裡（bar、面板的頭、
確認框），容器本身就答完了「這裡可以按」。給 ghost 加邊的代價很具體：確認框的取消鍵會變得跟旁邊
那顆 `.danger` 一樣重，而那一格是刻意讓「不做」比「做」輕的。

當前項目（`.active`）：頂部那一排畫 `1px solid var(--accent)` 加轉綠的字，**不填底**；底部 bar
維持純字轉綠。兩套不一樣是因為頂部那排密（36px 高排成一列），只靠字色分不出來；底部只有三項、
間距鬆，一個框反而在一條已經是面的 bar 裡多畫了一個面。

新增的 token：

| token | 亮 | 暗 | 用在 |
| --- | --- | --- | --- |
| `--surface-raised` | `#f0efe6` | `#211f1a` | 按鈕的 hover。暗色沒有影子可用，改用亮一階的底表示「抬起來」，在這之前暗色的 hover 用的是 `--surface-sunken`，比底還暗，按鈕反而縮下去 |
| `--line-actionable` | 同 `--line-firm` | `#6f695d` | 只給單獨站著的可按邊，跟分隔用的 `--line-hair` 分家 |
| `--line-track` | 同 `--line-firm` | `#4a4740` | Scrubber 的軌。它是唯一一條底下要墊著 fill 與 thumb 還得看得見的線 |
| `--surface-inverse` / `--text-on-inverse` / `--line-on-inverse` | 墨／紙／`--ink-700` | 骨白／夜黑／`--bone-300` | 只給浮動工具條 |

暗色三個新的灰接在 night 那一支上編號：`--night-700 #211f1a`、`--night-400 #4a4740`、
`--night-300 #6f695d`。

## Scrubber

**既有邏輯一律不動**：commit-on-release、拖曳中的預覽泡、`--scrubber-inset` 讓 0%／100% 落在端點、
方向鍵一步 1%、RTL 鏡射、`role="slider"`、索引建好前 disabled。

分岔三件事，而且**前兩件問 CSS、第三件問事件**：

- **粗細**（`any-pointer: coarse`）：fine 靜止 rail 3px／thumb 藏著，hover 時 rail 6px／thumb 14px；
  coarse **永遠** rail 6px／thumb 22px。沒有 hover 可以先問，所以形狀本身要把話說完。
- **inset**（`any-pointer: coarse`）：fine 10px，coarse 14px。22px 的 thumb 走到頭會有一半跨出 rail。
- **吸附章節邊界 ±2%**（`event.pointerType`）：手指與觸控筆吸，滑鼠不吸。**這一件不能用 media
  query**，`any-pointer: coarse` 在觸控筆電上永遠成立，而那台機器的滑鼠拖曳 1px 就該是 1px。
  純函式是 `lib/scrubber.ts` 的 `snapToChapter`，章節在軸上的位置由 frond 的 `Renderer.fractionAt`
  給（只有它的索引知道），**吸不吸附是 app 的政策**。書首書尾不讓：最後一章從 97% 開始是常態，
  吸走了讀者就永遠拖不到最後一頁。

暗色的值：rail 走 `--line-track`（暗色是 `--night-400`；原來的 `--line-firm #35322b` 對底只有
1.9:1）、thumb 加一圈 `0 0 0 2px var(--surface-page)` 的外圈，因為暗底上的黑影子等於沒有。

唯讀進度條維持另一套語彙，一個字都不動：`--text-muted`、3px、無端點、無 thumb。

## 浮動工具條

**位置邏輯完全不動。** `lib/toolbar-position.ts` 已經是「貼在選取範圍下方，會落進底部 96px 保留區
就翻到上方」，那個保留區是 Chrome for Android 從下緣推上來的原生搜尋條，JS 量不到、只能避開。
這跟指標型別無關。

只改長相，規則是「**跟身下的紙相反**」，不是「一直是黑的」：

| | 亮色 | 暗色 |
| --- | --- | --- |
| 底 | `--text-primary` | `--bone-100` |
| 字 | `--surface-sunken` | `--night-900` |
| 分隔線 | `--text-body` | `--bone-300` |

它是**唯一被允許反白的元件**，因為它是唯一蓋在讀者的字上面的東西。四個色點與兩個字之間有一條
`--line-on-inverse` 的分隔線：同一列上兩種東西。

色點維持現在的做法（臉 1.6rem、靶 `--tap-min`），另外在反白的底上補一圈 `--text-on-inverse` 的邊，
松煙與蓼藍貼在反白的底上會看不見，而那圈邊讓每顆點都有輪廓，又不必改掉讀者真正會拿到的墨色。
設計稿說「選中那顆」要包兩層 `box-shadow`，**這個工具條沒有選中狀態**：四顆色點是四個動作，按下去
就畫了，不是先選再套用。

楔子 14×7px（`clip-path`），顏色同工具條的底；工具條在下方時朝上、翻到上方時朝下，永遠指向選取
範圍那一側。

## 捲動

**整頁一根捲軸。** 不給封面牆自己的捲軸：讀者在牆上滾到底之後頁面不動，滑鼠移開兩公分再滾又是整頁
在動，同一個手勢兩種結果。

- 整頁 `scrollbar-gutter: stable`，抽屜開關的時候內容不橫跳。
- 抽屜開著鎖背後的頁面，抽屜自己那根捲軸留著。
- 閱讀器 `overscroll-behavior: none`，橡皮筋只有書架有。
- 翻頁的左右箭頭鈕在 600 以下收起來（原本的線是 700）。它問的是**視窗**不是手：那兩欄各 3rem，是窄
  視窗最缺的東西，而手指本來就用點的翻頁。改用指標問過，退回來了，模擬環境下引擎會回報整台機器只有
  觸控，桌機那一支就跟著消失，而 `tap.spec.ts` 正是在守那一支。

**封面牆分批載入不在這一輪。** 它需要的是一次量測（幾百本封面 blob 的解碼成本）而不是一個定案值，
而且它動的是 `Library.tsx` 的資料流，跟這一輪的骨架無關。

## 三種手

| 項目 | 滑鼠（fine+hover） | 觸控板 | 手指（coarse） |
| --- | --- | --- | --- |
| 命中區 | 最小 32px，密集列表 28px | 同滑鼠 | 一律 44px，抽屜列高 48px |
| hover 訊號 | 封面換邊色、rail 加粗、`⋯` 淡入 | 同滑鼠 | 沒有 hover，改為 `:active` |
| 可拖曳怎麼被看出來 | 靜止細，hover 變厚 | 同滑鼠 | 永遠厚版＋端點＋thumb |
| 拖進度軸 | 1px = 1px，放手才跳 | 同滑鼠 | 同左（吸附另計） |
| 翻頁 | 點擊叫 chrome、方向鍵翻頁 | 同滑鼠 | 下三成分左右半翻頁、橫滑 50px |
| focus 可見度 | Tab 走訪，封面用裁切標記 | 同滑鼠 | 外接鍵盤時同左，**不因為是觸控就關掉** |
