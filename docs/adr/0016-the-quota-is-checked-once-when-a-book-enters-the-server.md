# 額度只在書進伺服器那一次檢查

日期：2026-08-11，2026-09-02 改寫。前一版〈付費牆是兩道門，不是一道〉的決定是：建帳號那一次檢查
付款，之後每一次請求檢查訂閱，因為那時候沒付款就沒有帳號。
[ADR-0011](0011-the-account-is-free-and-the-quota-is-paid.md) 改寫之後帳號免費，建帳號時沒有
東西可檢查了，之後也不必每一次請求都檢查。

## 決定

ADR-0011 決定了收費的**界線**：帳號免費，三本以上收費。這一份決定那條界線**擋在程式的哪裡**。

**額度只檢查一次，在一本書要進伺服器的那一次**：Worker 收到一本它沒見過的書，算這個帳號同步的書
滿三本了沒。沒滿就收下；滿了就拒絕，那本書留在裝置上。

其餘請求**不檢查額度**：已經收下的書，它的閱讀位置、筆記、閱讀時段照常進出；`/mcp` 也不檢查，
它讀的是 D1 與 R2，看得到的本來就只有已經在伺服器上的書。

## 為什麼在這裡檢查

額度的定義是「伺服器上有幾本這個帳號的書」（〈同步中的書〉），所以唯一會改變它的動作就是
一本新書進來。在那一次擋住，其他地方就沒有東西可擋：沒被收下的書在伺服器上一個位元組都
沒有，後面的請求不可能碰到它。

前一版「每一次請求檢查訂閱」的理由是要讓「有帳號、訂閱停掉、資料還在」活得下去。那個狀態現在
仍然合法，但表達它的不是每次請求的檢查，是**額度縮回三本**：訂閱停掉時 Worker 把最近讀過的三本以外的書
標成凍結，凍結的書不收變更、MCP 看不到。這是一次性的動作，不是每次請求的判斷。

## 先送到的先算，不是 client 說的順序

Worker 只知道一件事：這本書現在到了，這個帳號滿三本了沒。它不看 client 的加入時間，也不接受
client 自己排的「這三本」。理由在 ADR-0011：兩台裝置各自離線加書，各自的時鐘與順序都不可信，
只有伺服器給得出唯一的答案。

額度滿了不是錯誤，`POST /api/sync` 照樣回 200，只是沒被收下的那本書連同它的閱讀位置、筆記、閱讀時段
一起不寫進 D1。client 不靠回應判斷，靠 `/auth/me` 回的 `synced` 清單：伺服器說哪幾本在同步，不在
清單上的就是「伺服器不收」，書留在裝置上、書架上標一個記號、〈帳號〉抽屜裡有升級入口。要重試的
只有真的壞掉（非 2xx）的那種。

## `/mcp` 不檢查額度，但凍結要寫進它讀的地方

`worker/index.ts` 分成兩半：`/api/*` 認的是 session cookie，`/mcp` 認的是 OAuth access token，
它只有 `OAuthProvider` 叫得到，不經過另一半的任何一行。前一版因此要把訂閱檢查寫兩次。

現在 `/mcp` 那一半不用檢查額度，但**凍結**要對它成立：agent 列書、搜尋、取節的時候，凍結的書不能
出現。那不是額度檢查，是 store 查詢的條件，跟 `deleted_at IS NULL` 同一個位置。

閱讀位置與筆記那兩條查詢也一起過濾，而且連刪掉的書一起擋：書架上看不到的書，它的位置與筆記
也不該出現。最明顯的例子是「我讀到哪」不帶書名的時候，挑的是整張 `progress` 表裡最近的一筆，
不擋的話它會挑到一本凍結或刪掉的書，接著開檔失敗、回一個「檔案沒上傳完」的錯誤。

## 訂閱過期時不撤銷已發出的 token

訂閱過期不撤銷 access token：撤銷之後使用者續費，得回到 Claude 或別的 agent 重跑一次 OAuth
授權，而那件事他上一次做的時候大概花了五分鐘找設定在哪。token 留著的話，續費當下額度回到
無上限、凍結解除，什麼都不用做。

## 沒有東西可買的部署，就沒有額度

**這個部署有沒有接金流，決定新帳號拿到的是三本還是沒有上限。**接了就是三本，沒接就是沒有上限。

判斷的依據是那五個 Paddle 設定值有沒有設（見 `worker/billing.ts`）。都沒設的話 `/billing/*` 整組
回 404，而這個部署上的帳號一律沒有上限。

⚠️ **這條規則寫在 `bookLimitOf()`，不寫在建帳號那裡**，而那個位置是重點：額度是從**當前設定**算出來
的，不是建帳號那一刻凍結下來的答案。寫在建帳號那裡的話，規則只對之後建的帳號成立，而 D1 那一欄會
留著一個沒有人會回頭改的舊答案。migration 0007 正是這樣的來源，它把每個既有帳號設成三本，而 SQL
沒有辦法問「這個部署收不收得到錢」。

那一段會**寫回資料庫**（`setBookLimit(null)`），不是只回一個 null：額度與凍結必須一起動，否則同步的
push 會繼續拒收那些書、`/mcp` 也繼續看不到它們。條件跑過一次就不成立了，所以那是每個帳號一次的寫入。

理由：**額度要有意義，得先有一條解除它的路**。自架的人跑的是自己的 Cloudflare 帳號、自己付
Cloudflare 的錢，那個部署上的三本收不到任何人的錢，只會讓讀者按了升級鈕之後發現沒有東西可以買。
所以沒接金流的部署乾脆不設限。

⚠️ **設了一半要吵。**「我不接付款」與「我漏填了一個」的正確反應剛好相反：前者要安靜地關掉，
後者要大聲。而這兩件事在程式眼中長得一樣，所以分成兩層檢查：三個 build variable 少填在**部署時**
就停下來（`scripts/deploy-config.ts`），另外兩個 secret 是 `wrangler secret put` 設的、build 環境
讀不到，所以少了 secret 的那種只有**跑起來的 Worker** 看得見，它回 500 加一行 log，不回 404。

不分開的話，設了一半的部署會是這樣：部署綠燈、升級鈕出現在畫面上、讀者按下去之後 Worker 拿著沒
設好的值去打 Paddle，失敗，而在那之前沒有任何一個地方說過話。

⚠️ **「沒設」跟「設了一半」要分開。** 設了一半是壞掉，不是免費，所以那種部署上的帳號拿到的是三本，
不是沒有上限。因為額度每次都重算，補上漏掉的那個 secret 之後不必回頭修任何一列資料。

## 白名單那批人沒有上限（改成自架的機制）

以前這條是上線前的特例：〈開放註冊〉之前建的帳號不受額度管，不設期限。

**現在它的身分變了**，變成上面那條規則的一個結果，不再是特例。接了金流的部署上，migration 0007
把所有現有帳號設回三本，**包括維護者自己的**；維護者用永久 100% 折扣碼走正常的訂閱流程開通自己，
跟任何一個讀者走同一條路。

**那支 migration 連凍結一起做完**，不是只改 `book_limit` 那個數字。⚠️ 這一點值得寫下來，因為凍結
平常是 `setBookLimit()` 的工作，而 migration 是 SQL，叫不到它，所以那段規則在 migration 0007 裡
用 SQL 寫了第二遍，**兩邊必須一致**：留最近讀過的三本（沒開過的書算在它加入的時間），其餘凍結，
同分用 id 決定。

只改數字會留下一種**別的路徑都產生不出來的狀態**：額度三本，但 50 本全都還在同步中。那不算壞掉
（額度只擋沒見過的新書，見上面〈決定〉），但〈帳號〉抽屜會顯示「50 本中的 50 本在同步」，而任何
一個要處理額度的人從此都得先問「這個帳號是哪一種三本」。**狀態少一種，比那支 migration 短幾行值錢。**

為什麼要改：那條特例本來的理由是「他們明知資料會被清掉才進來」，而那個理由在
[ADR-0004](0004-development-phase-and-launch-line.md) 的〈上線〉之後就用完了。留著它會變成一份
只有一個人查得出來、也沒有任何一段程式在描述的名單。而**維護者自己走一次真的結帳**還順便驗證了
這條路真的能走。
