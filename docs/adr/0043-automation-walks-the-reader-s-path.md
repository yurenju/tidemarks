# 自動化走的是使用者走的那條路

日期：2026-08-29。

## 決定

要讓自動化到達某個畫面狀態的時候，**加一個網址參數，走使用者走的同一條路**，不加一個只在開發版存在的
後門。

第一個這樣做的是 `?select=`（#128）：它把一段字選起來，接下來顏色列怎麼浮出來、點下去怎麼畫成一條線，
每一步都跟真人做的一模一樣。它的兄弟是 `?at=`（#127）。

跟著這個決定的三件事：

| | 決定 |
| --- | --- |
| **它是公開介面** | 進了網址列就是別人會依賴的東西，所以要有測試，改法要向後相容 |
| **但它不是畫面上的字** | 沒有任何 UI 會產生這種網址，也沒有一個字會出現在畫面上，所以不進 catalog |
| **失敗只寫 console** | 用它的人是打字打出來的那一個，跟看得到 console 的是同一個人 |

## 被拒絕的那個做法

原本打算掛一個只在 dev build 存在的 `window` 函式，例如 `window.__tidemarks.select(cfi)`。它比較好
寫，而且「這是測試工具」這件事寫在名字上。

它的代價是**測到的東西跟出貨的東西不是同一個**。一個只在 dev build 存在的入口，走的是一條沒有人在
production 走過的路：它繞過網址解析、繞過開書的次序、繞過「什麼時候算到位」那一整段判斷。而截圖與收尾
驗證正是拿來證明「這個功能真的長這樣」的東西；從一個專用入口產生的畫面，證明得了的只有那個入口。

反過來說，走網址就沒有第二條路可以走岔：`?select=` 讀完之後接上的是 `Reader.tsx` 裡真人選字接上的那同
一個 `showRange`，或是瀏覽器自己的選取事件。

## 為什麼這個要寫下來，`?at=` 沒有

`?at=` 是讀者自己會用的東西：把「我讀到這裡」這個網址寄給自己或別人。它是產品功能，不必解釋。

`?select=` 不是。沒有一個讀者會想寄一個「幫我把這句話選起來」的網址，它從頭到尾是為了截圖與驗證而存在
的。所以下一個讀到它的人會問「這既然只有開發在用，為什麼不做成開發專用的東西」，而上面那一節就是答案。

## 這條規則怎麼用

碰到「自動化到不了某個狀態」的時候，先問**這個狀態使用者是怎麼到的**：

- **使用者走網址到得了** → 加參數，讓自動化走同一條。
- **使用者是用手勢到的**（長按、拖曳、捏合） → 那就得真的做那個手勢，這條規則管不到。
  `touch-selection.spec.ts` 的長按不會因為有了 `?select=` 就換掉：那些測試要驗的正是長按本身。
- **使用者根本到不了**（只有壞掉的時候才會出現的狀態） → 那要在測試裡自己造出來，不要為它開網址參數。

⚠️ **加參數的門檻不低。** 每加一個都是一個要維護到永遠的公開介面，所以要換到的東西必須是「不加就得
模擬一段每次結果都不一樣的操作」。`?select=` 換掉的是模擬拖曳，而拖曳選到幾個字每一次都不同，那正是
它值得的理由。純粹「這樣寫比較短」不算。
