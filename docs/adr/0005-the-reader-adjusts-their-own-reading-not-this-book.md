# 讀者調的是自己的讀法，不是這本書的排版

日期：2026-07-31，2026-08-17 改寫。前一版〈排版設定跟著裝置，也跟著書，但不跟著讀者〉是兩層：一份
裝置預設，加上每本書可以蓋掉其中四項。

⚠️ 行距的「書籍預設」有一個例外，由 [ADR-0032](0032-a-mark-goes-beside-the-text-and-nothing-else.md)
訂下：書自己的行距緊到螢光的波浪畫上去就會碰到字時，會被撐到剛好夠。只有這一格，只有不夠的時候，
只補到剛好夠。底下那句「一個沒調過任何東西的讀者，拿到的就是書自己的排版」要照這個範圍讀。

早先的安排是兩層：一份裝置預設加上每本書可以蓋掉四項。這裡把它收成一層。

## 決定

**排版設定只有一層**，六項全在（主題、字型、欄數、字級、行距、留白），存在這台裝置上，
**而且只存在這台裝置上**：不進 Dexie、不進 sync payload。

- **調了就是每一本都調。** 沒有「這一本」與「所有書」兩種範圍，所以也沒有「以後每本書都這樣排」
  那顆按鈕。剩下的唯一一顆是「回到預設值」。
- **`folis-book-overrides` 廢掉**，不再讀也不再寫。`BookOverride`、`effectiveSettings`、
  `promoteToDefault`、`loadOverride`、`saveOverride`、`clearOverride` 一併消失。
- **直排與橫排共用同一組字級與行距**，不各存一份。
- 六項因此只有一個家，而它有兩個入口：閱讀時是〈排版〉面板（疊在書上，上面留著真的書當預覽），
  在書架上是〈設定〉這一層樓的〈排版〉tab。**兩邊是同一個表單元件**，不是兩份長得像的程式碼。

## 為什麼不同步：這是刻意的，不是漏掉

進度、筆記、書本身全部都同步，唯獨這一份不同步，所以它看起來像沒做完。而且它做得到：books 表
有同步，同一本書在手機與電腦是同一個 bookId。缺的不是機制。

不同步是因為**這些設定回答的問題本來就跟裝置有關**：字級在回答「這個螢幕多大、我離它多遠、我戴
不戴眼鏡」，留白在回答「這個視窗多寬」，欄數更是直接在回答視窗寬度。同一個讀者在 6 吋手機與
27 吋螢幕上的正確答案不同，同步過去只會把另一台調好的設定弄壞。

**存在 localStorage 而不是 Dexie，本身就是這個決定的宣告。** Dexie 那五張表每一張都有 `dirtyAt`、
每一張都在 sync payload 裡；放進去就會有人問「為什麼這張表沒有 `dirtyAt`」。

**介面語言走同一條路**：`tidemarks-locale` 跟 `tidemarks-settings` 當鄰居，不進 Dexie
（[ADR-0031](0031-english-is-the-source-and-chinese-becomes-a-translation.md)）。語言回答的是「我
手上這台機器是誰在用、在什麼環境下用」，不是「我這個人偏好什麼」。多出來的一件事是**信**：登入信
是伺服器寄的，而伺服器不知道這台裝置選了什麼，所以 app 送出的每一個請求都帶 `Accept-Language`
（`src/lib/api.ts`），Worker 照那個回答。**不存進帳號**，存了就要回答「兩台裝置設不同語言時帳號
算哪個」，那題沒有好答案，而且問題本身是「跟著帳號」才生出來的。

## 為什麼兩層是錯的

當初選兩層，假設的是讀者會想為某一本書做特別的安排。實際用下來不是這樣：**每開一本新書都調成
同一組值**。那組值不是關於哪一本書的主張，是關於這雙眼睛與這個螢幕的主張。

真正的毛病不在「有兩層」，在**寫入的方向反了**。讀者九成的動作是「我想這樣讀書」，而系統把每一次
調整都讀成「我想這本書這樣」，要改預設得另外按一顆按鈕。舊規則還加了一條：把某一項調成跟預設
一樣的值也算主張。於是隨手拉一下行距，那本書就永久脫離預設了，而畫面上沒有任何一個字說過這件事。

而這個代價當初就寫下來過：「閱讀器面板上會同時有兩種範圍的控制項，而它們長得一模一樣」，
然後它真的發生了：兩個選單、四項重複、範圍只靠面板底下一行小字說明。

## 為什麼不採 Thorium 的方向

[Thorium Reader](https://github.com/edrlab/thorium-reader/discussions/3127) 是唯一一家留下轉向
理由的：它**原本是全域一份，後來刻意改成每本書一份**，因為 EPUB 各家作者的樣式差異太大，
「the automatic application of the same reading system overrides for all ebooks resulted in a
bad user experience」。方向跟這裡相反，所以值得正面回答。

Folis 對那個坑有一半的免疫力，而且是設計出來的：字型預設是「書籍預設」（不介入）、行距預設是 0
（也是不介入）、字級是相對於讀者 root 的百分比而不是絕對值
（[ADR-0006](0006-font-size-is-a-percentage-of-the-readers-root.md)），frond 會把書自己的絕對
尺寸相對化。**一個沒調過任何東西的讀者，拿到的就是書自己的排版。**只有在讀者主動把行距或字型從
「書籍預設」改掉之後，才會遇到 Thorium 講的那件事，而那時候他是在明確地說「我不要這本書的安排」。

更重要的是：Thorium 的解法會把這裡要修的痛點原封不動搬過來。每本書從預設值起算，等於每本書都要
再調一次。

要接住 Thorium 那個風險，[Readest](https://github.com/readest/readest/wiki/Custom-CSS-for-Styling-Books-and-the-Reader-UI)
的形狀比較對：預設寫全域，每一節有一個看得見的 `Global Settings` 勾選框，取消勾選才變成單本覆寫。
那條路隨時加得回來，而且加回來的時候方向是對的。

其餘各家的做法整理在
[docs/specs/reading-typography/prior-art.md](../specs/reading-typography/prior-art.md)。

## 為什麼直排與橫排共用一組值

因為沒有證據說它們該分開，而且**十三家閱讀軟體裡沒有一家找得到第一手證據**顯示直橫排各存一組
字級行距。KOReader 與微信讀書更直接，兩家根本不支援直排。

這是「現在不做」，不是「決定不做」。回頭的證據要長這樣：**同一台裝置上讀一本直排書與一本橫排書，
兩次都想把字級調到不同的數字。** 沒有這個條件，這件事會每半年被重問一次。

## 代價

**「這本詩集要大字」做不到了。** 這是真的損失，只是它換到的東西更值錢：每一次調整的效果都是可預測
的，而且不必先搞懂自己站在哪一層。

**開發階段的資料直接丟。** 既有的單本覆寫不撈、不合併、不挑一本當新的預設，那個 localStorage key
直接清掉（[ADR-0004](0004-development-phase-and-launch-line.md)）。撈的話得先回答「挑哪一本」，
而任何答案都是猜的。

**〈設定〉從抽屜變成一層樓。** 六項的家搬進 `#/settings/typography` 之後，〈帳號〉也跟著變成同一頁
的 tab，原本的〈設定〉抽屜就不存在了。這動到介面的分類方式，怎麼分寫在 CONTEXT.md 的〈畫面〉
〈抽屜〉〈面板〉三條。返回鍵怎麼疊在
舊 repo 的 #157 決定。

## 反過來的證據

如果哪天出現一本書，它的排版糟到讀者必須為它單獨設定，而且那個設定不該擴散到別的書，那就是
Readest 那條路該補上的時候：**預設仍然寫全域，加一個看得見的逃生門。**注意順序，這跟先前那個
兩層不是同一件事：那時候的預設方向是單本，逃生門是「設為預設」。

如果反過來，讀者開始想要「白天一組、晚上一組」或「通勤一組、書桌一組」，那問的就不是覆寫，是
Kindle 的 saved themes 與 Calibre 的 Profiles 那種東西：**多組全域設定之間切換**。那也不是這支
ADR 要接的，但它會先偽裝成「我想為這本書設定」出現，所以值得先認得它。

## 後續：「留著真的書當預覽」這件事，寬視窗與窄視窗的付法不同

上面第 18 行寫的是〈排版〉面板**疊在書上**。後來桌機改成把面板放到書**旁邊**、書讓出一個欄
（`docs/specs/ux-replan/spec.md`），那不是推翻，是同一個要求的另一種付法：預覽要成立，讀者
拖字級的時候看得見的就得是真的頁面，而「疊上去」與「擠到旁邊」都做得到，只是後者要付一次重新分頁。

2026-08-19 補上的條件是：**那個付法只在視窗夠寬的時候划算。** 分界寫在 `index.css` 的
`@media (min-width: 1024px)`。理由是算得出來的：900px 的視窗把 300px 交給面板，書只剩 600px，
那是一欄字加三分之二頁，預覽是保住了，被預覽的東西卻已經不是讀者平常在讀的版面。所以窄視窗
回到「疊在書上」，而且它反而拿回了一樣東西：**完全不重新分頁**。

同一批改動還把面板的寬度從定值 236px 換成 `clamp(300px, 24vw, 420px)`。這跟這支 ADR 的主張無關
（它管的是設定有幾層），但它是上面那條算式裡的變數：面板佔多少，決定了「讓出一欄」從哪個寬度
開始划不來。兩個數字都是判斷不是量測，真的書的目錄如果說不通，該動的是它們，不是 1024。
