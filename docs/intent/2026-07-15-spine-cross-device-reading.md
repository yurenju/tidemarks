# 意圖核心：Spine 跨裝置閱讀

## 一開始想做的

> 原本這是一個前端的程式，如果我想要改成後端用 cloudflare 作，然後改成支援離線閱讀的 pwa，可以採取怎樣的技術結構？另外我也希望可以支援 mcp，比如說可以從特定路徑開始讀書、討論內容並筆記之類的。
>
> 我第一個想到的就是使用者認證應該要採用 mcp 更兼容的方式。

追問意圖時，換了一種說法：

> 我想要作的事情是可以在手機上閱讀，然後可以同步閱讀進度到電腦上，然後也會想要用 claude 來解釋我目前看到的部份。

## 問下去之後

一開始講的是一套技術結構：後端、PWA、MCP，而且最先擔心的是認證要怎麼做才跟 MCP 相容。認證被放在第一位，暗示這件事被當成一個「要蓋一個系統」的題目。

但問到「為什麼要跨裝置接續」時，答案沒有落在方便性上，而是落在「有沒有在讀」。摩擦一大就不讀了，書就這樣放著。這是個層級不同的答案：它講的不是這個 app 好不好用，是它有沒有在發揮作用。

再問下去，摩擦的位置就具體了：**在手機上匯入 epub 太麻煩了**。合理的樣子應該是在電腦上匯入之後，書自己出現在手機裡。

順著這條線回頭看，「同步閱讀進度」其實只是這件事的一半，而且是比較小的一半。真正的分工是：電腦是管理裝置，手機是消費裝置。手機上任何需要「管理」的動作，都發生在想讀書的那一刻，也就是最沒有耐心的那一刻。

至於 Claude，它的位置也跟著清楚了：是看書遇到問題時可以問的對象，不是這件事的主軸。

## 根因

**手機是消費裝置，不是管理裝置。書必須在電腦上匯入之後自己出現在手機裡；手機端的正確管理動作數量是零。摩擦決定的不是好不好用，是有沒有在讀。**

這個 app 最終想做成別人也能用的，但第一階段只有自己用，當作測試。所以架構上不能把自己鎖死在單人，但第一版不需要註冊流程。

登入只做 passkey，不做密碼、不寄 email 或 SMS。這條跟根因同向：驗證信是摩擦，簡訊也是，削的是同一個東西。技術上它跟 MCP 正交，`workers-oauth-provider` 不管使用者怎麼認證，passkey 唯一的工作是生出 `completeAuthorization({ userId })` 需要的那個 id。

> 遇到本文件沒寫到的狀況時這樣分：先問這個選擇會不會在手機上多長出一個步驟，會的話就不要。再來是不要引入第二個廠商或第二個部署環境。

## 所以要做什麼

整套做在 Cloudflare 上：Worker 跑 MCP server 與 OAuth AS，R2 放 epub 檔本體，D1 放書籍 metadata、進度與筆記，前端改成 PWA。第一版只開自己一個帳號，但資料模型從一開始就帶 `user_id`。

原本想的東西方向沒錯，但**排序錯了**。認證被放在第一個煩惱的位置，可是它其實是被 MCP 規格逼出來的副產品，不是這件事的核心。核心是「電腦匯入 → 手機自動出現」這條路徑，而那條路徑跟認證幾乎無關。

- **不選「用雲端硬碟當同步層」**：幾乎不用寫後端，但 MCP 沒有立足點（Claude 連不到本機資料夾），而且手機瀏覽器讀雲端資料夾做不乾淨。
- **不選「單人版：R2 + 一把 secret，不做 OAuth」**：這是最省工的做法，但目標是做成別人能用的，這條路會把自己鎖死，之後要拆掉重來。
- **不選「local stdio MCP，省掉整個 OAuth」**：技術上可行且省掉最大一塊工，但它要在電腦上長一個常駐的東西，那正好是「環境單純」要避免的第二個環境；而且手機上就問不了 Claude。
- **不選 Supabase 或混合方案**：理由是環境單純。Supabase 的 OAuth server 目前 token 沒有 audience binding（`aud` 是固定字串），不符合 MCP 規格對 token 綁定的要求；混合方案雖然兩邊的接縫乾淨，但多一個廠商就多一套部署與 secret。

## 驗收：做出來的東西跟講好的一樣嗎？

- 在電腦上匯入一本 epub 之後，**不在手機上做任何管理動作**，手機打開 app 就看得到那本書。
- 手機讀到某個位置，電腦打開時接在同一個位置；反向亦然。
- 手機端從「想讀」到「讀到」的動作數：點開 app、點書、開始讀。沒有第四步。
- 從手機的 Claude 問「解釋我現在看到的段落」，Claude 拿得到當前位置的內容，不需要手動貼上。
- 已下載的書在離線狀態下可以讀。
- 資料模型帶 `user_id`，第二個使用者可以在不改 schema 的前提下加進來。
- 登入全程沒有密碼、沒有驗證信、沒有簡訊。
- 註冊時強制產生 recovery code 並要求使用者確認已存好，且明白告知「passkey 全部遺失且 recovery code 找不到，帳號就是沒了」。這是選 A 的代價，代價必須說出口，不能藏起來。

## 回顧：當初想的對嗎？

- 問題：摩擦降到零之後，你真的變得比較常讀書嗎？還是會發現不讀的原因根本不是摩擦，而是別的東西（沒時間、書選得不對、注意力被別的東西吃掉）？如果是後者，那這整套東西解的是一個不存在的問題。
- 附帶問題：Claude 那塊真的有在用嗎？還是它其實是「聽起來很好但實際上不會做」的功能？
- 什麼時候回來看：上線自己用滿一個月之後。如果那時候一本書都還沒讀完，那更值得看，因為那正好是這個問題最誠實的答案。

另一個要單獨回來看的問題（開放給別人之前）：

- 問題：只給 recovery code、不給任何 email 復原，這個代價由誰承受？自己一個人用的時候它趨近於零，但第一個弄丟所有 passkey 又找不到 recovery code 的使用者出現時，你只能跟他說筆記沒了。到那個時候，你還會做同樣的選擇嗎？
- 什麼時候回來看：**決定要開放給第一個非自己的使用者之前**。這題有時效性：事後補 email 復原對已存在的帳號補不上，只能請所有人回來重填。自己一個人的時候改很便宜，有 50 個使用者的時候就不便宜了。

### 2026-08-09：回來看了

**答案是不會。** 登入改成 passkey 與 email + magic code 兩把平行的鑰匙，recovery code 拿掉。決定與代價寫在 [ADR-0015](../adr/0015-an-account-is-only-as-strong-as-its-inbox.md)。

這題自己指定的時機到了（要開放給第一個非自己的使用者之前），而且是在帳號數還是 1 的時候處理的，所以「請所有人回來重填」那個代價一次都沒有發生。

這份文件有兩處因此被推翻，原文留著不動，因為那是當時真的這樣想：

- **「登入只做 passkey，不做密碼、不寄 email 或 SMS」**（〈根因〉）與驗收條件**「登入全程沒有密碼、沒有驗證信、沒有簡訊」**。驗證信確實是摩擦，這一點沒有講錯；講錯的是把摩擦當成唯一要衡量的東西。**「弄丟 passkey 就是筆記沒了」不是摩擦，是損失**，而摩擦只發生在註冊那一次，損失是永久的。
- **「不要引入第二個廠商或第二個部署環境」**（〈根因〉的分法）。寄信要一個廠商（Resend），所以這條**收斂成「不要引入第二個部署環境」**：它當初擋掉的是 Supabase，理由是「多一個廠商就多一套部署與 secret」，而純 API 的服務沒有那個東西。理由見 ADR-0015。

沒有被推翻的是根因本身。**手機端的管理動作數還是零**：magic code 只在註冊那一次要收信，之後那台裝置上就有 passkey 了。
