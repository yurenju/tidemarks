# 一個測試憑什麼留著

[CLAUDE.md](../../CLAUDE.md) 的〈測試分層〉講的是**東西放在哪一層**：四個 vitest project 各蓋什麼、
瀏覽器那套為什麼進容器、worker 那層為什麼不進。那些問題都已經有答案。

這份文件管的是上面那一層，而它一直沒有寫下來：**這條測試該不該存在。**

## 那句話

> **每個測試都要說得出它測到的角度，而那個角度是其他層次的測試測不到的；答不出來就刪。**

兩個條件都要成立。「測到一個角度」很容易——任何一條測試都測到了某個角度。難的是第二個：
**那個角度別的層測不到嗎？** 測得到的話，這條就是同一件事的第二份副本，而副本不會讓你更早發現
問題，只會在你改實作的時候多一個地方要改。

「刪」是預設，不是威脅。這裡沒有「多測一點總是比較安全」這回事——每一條測試都是一份要跟著產品
一起改的敘述，寫下去就一直在收費。

## 層有高低，越上面門檻越高

由低到高：

| 層 | 測得到的角度 |
| --- | --- |
| **node** / **scripts** | 純函式的輸入輸出。規則本身對不對 |
| **worker** | 真的 workerd 加真的 D1／R2：欄位名、`bind()` 的次序、某條路沒有 token 進不進得去 |
| **frond browser** | 真的排版引擎量出來的幾何：字符寬度、矩形、分頁 |
| **app browser** | 真的人在真的書上做的事：手勢、面板、跨元件的流程 |

**往上一層，門檻就高一階。** 要在 app browser 加一條，得先說得出 node 那層為什麼測不到。答案通常是
「因為它需要真的版面」或「因為它跨了三個元件」——這兩個是好答案。「因為這樣比較保險」不是。

## 五條原則

### 1. 一個命題只在最低能證明它的那一層測窮盡，上層最多留一條接線

現成的例子。行寬規則（表意文字上限 40em、拉丁文 30em、太短就不分欄）在純函式層
[line-length.test.ts](../../packages/app/src/lib/line-length.test.ts) 測得很完整：

- `caps an ideographic line at 40 ems and turns the rest into margin`
- `caps a latin line at 30 ems`
- `is single column whatever the reader asked for`

然後瀏覽器層的
[line-length.spec.ts](../../packages/app/tests/browser/reader/line-length.spec.ts) 把同樣三個命題
**再證一次**：

- `stops a latin line at 30 ems however wide the window gets`
- `stops a vertical line at 40 ems, measured down the page`
- `does not split into two columns that would each be too short`

**規則：同一個命題在上層最多留一條接線測試。** 接線測試只回答一件事——「下層算出來的那個數字，
真的到了畫面上」。餵一個已知輸入，量一次，比對。它不再逐個情境重跑，因為那些情境下層已經走完了。

**為什麼不是零條。** 因為「算對了但沒接上」在這個 repo 是真的會發生的：樣式是八個檔案靠 `@import`
的次序決勝負，沒有 `@layer` 也不靠 specificity，而 `device.css` 裡有 29 個選擇器在覆寫前面設過的
規則。純函式回傳 `40em`，元素上卻是別的值，兩層都綠——這一類只有真的量畫面才看得到。

**為什麼不是三條。** 第二條之後就不再證明「接起來了」，只是把下層的表格抄到上層再跑一遍，而上層
一條要 ×3 個引擎。

**「一條」的粒度是一條規則，不是一個檔、也不是一個斷言。** 行寬上限是一條規則，它在下層有三個
情境（表意文字、拉丁文、太短不分欄），上層合起來留一條。但同一個檔裡的「控制項移動時版面跟著動」
是**另一條規則**（走的是另一段程式），它有自己的一條。判斷的方式是問「這兩條測試如果壞了，是不是
同一個地方壞了」——是的話同一條規則，不是的話各自算。

**選哪一條留下來。** 挑**接線斷掉時失守最多的那一條**。行寬那組留的是直排那條，因為接線會斷的東西
有兩件——數字，以及它躺的軸——而直排那條兩件都帶著，拉丁那條只帶第一件。留下來之後把測試名稱改成
接線的意思（「把算出來的上限帶到頁面上」），不要留著原本那個聽起來像在測規則的名字。

**代價寫在這裡，不要假裝沒有：** 我們接受某些跨層情境沒有測試守著。判斷是——接線斷掉的話，那一條
接線測試就會紅；接線是通的，下層的規則就作數。中間那塊（接線通、但只在某個特定情境下錯）沒有東西
守，換到的是不用維護三份同義的斷言。

⚠️ **不是所有同名的都是重複。** 同一個 `line-length.spec.ts` 裡的
`moving the margin control moves the layout`、
`takes the choice away over a vertical book, where frond cannot honour it` 測的是控制項與直排書
把這個選擇收走——那些**沒有**純函式版本，是這一層獨有的角度。判斷的方式是逐條讀命題，不是看檔名。

### 2. 測試基礎設施只測它沒有漂移，不測它產出的內容長什麼樣

frond 的合成 fixture 是程式產生的，所以「產生器對不對」是個真問題：fixture 錯了，frond 那四百多條
會一起變成**假綠燈**，而假綠燈是別的層絕對看不到的。

但要分清楚兩種：

- **守門的**——[determinism.test.ts](../../packages/frond/tests/node/test-fixtures/determinism.test.ts)
  （產兩次比 hash）、[committed-fixtures.test.ts](../../packages/frond/tests/node/test-fixtures/committed-fixtures.test.ts)
  （repo 裡的檔案 vs 產生器輸出）。它們測的是「這批東西沒有在你不知道的時候變了」。留。
- **驗產物形狀的**——用 regex 斷言產生出來的 stylesheet 裡有什麼。這一類要問一句：
  **產生器如果寫錯，用它的那些測試會不會自己紅？** 會的話，這條就沒有測到別人測不到的角度。

分辨的方法只有一個問題：**這個檔紅的時候，有沒有別的東西也會跟著紅？** 只有它紅，它就是守門的；
一片跟著紅，它只是最早喊出來的那一個，而最早喊不值一條測試。

**這個問題要真的去試，不要用讀的。** 把產生器改壞、跑一次、看誰紅、還原。兩個地方會出錯：

⚠️ **fixture 要重新產。** 產品層讀的是 repo 裡 committed 的 `.epub`，**不是產生器**。只改產生器就跑
測試，一條都不會紅，而那個答案跟事實完全相反。順序是：改壞 → `npm run fixtures` → 跑測試 → 還原
→ 再 `npm run fixtures`。

⚠️ **「跟著紅」跟「無聲通過」要分開。** fixture 失去症狀之後，上層那條測試是**變紅**，還是**變成
一條空過的測試**？空過的才是真正危險的——它還在那裡、還是綠的，但已經什麼都沒有驗到。舉例：
「空的 section 不會讓 fraction 變成 NaN」這條，需要 fixture 裡真的有一個空 section；fixture 少了它，
那條測試不會紅，它只是安靜地不再測任何東西。**只有會變紅的才算「有別人代它報告」**，會變成空過的
那些，守門的那一條要留著。

### 3. 依賴外部或平台的假設，可以獨立成一條

[decompression-stream.spec.ts](../../packages/frond/tests/browser/smoke/decompression-stream.spec.ts)
斷言三家瀏覽器的 `DecompressionStream('deflate-raw')` 真的能解壓。這看起來像在測瀏覽器而不是測我們
自己的程式碼，而它確實是——但它測到的角度是別的層沒有的：**這個平台假設如果哪天不成立，會有一條
獨立的紅燈直接說出是這件事**，而不是表現成一整批莫名其妙的解析失敗。

條件有兩個，兩個都要：**獨立成一條**（不混在功能測試裡），而且**失敗時直接指出是哪個假設**。
順手在功能測試裡多驗一下平台行為的，不算，那是要刪的那種。

**跟原則 1 分不清楚的時候問這句：這條測試如果紅了，我會去看誰的程式碼？** 去看自己寫的那個 transform
——那是原則 1 的副本，下層已經證過了。要去看瀏覽器的 release notes——那才是原則 3，留著。

現成的一組對照：`css.test.ts` 證明前綴改寫的字串轉換對不對（紅了看自己的程式碼），
`writing-mode-declaration.spec.ts` 證明三家引擎認不認那個拼法（紅了看引擎變了什麼）。
兩個檔名字很像，測到的角度完全不同。

### 4. 每個測試檔的檔頭寫一行：這個檔測到的角度

不是每個案例——那會變成註解垃圾。是**檔案**層級一行，說出這個檔存在的理由。

這一行不是格式要求，它是**判斷的結果**。寫不出來的那個檔，當場就是候選。所以它同時是規則和篩子。

**放在檔案第一行，`import` 之前，一到四行。** 兩個理由：它要是打開檔案第一眼看到的東西，而且放
第一行才機械檢查得了（`head -1`）。

⚠️ 這個 repo 有些測試檔在 import 之後放了一段 `/** */`，寫得又長又好——踩過哪本真書、為什麼這樣
量、引到哪一支 ADR。**那些留在原地，不要往上搬。** 兩段的職責不同：

| | 放哪 | 回答什麼 |
| --- | --- | --- |
| 檔頭那一行 | 第一行，import 之前 | **這個檔測到的角度，以及隔壁那一層在哪** |
| 既有的 docblock | 原地，import 之後 | 背景：怎麼發現的、為什麼這樣測、代價是什麼 |

**兩段不要講同一句話。** 補檔頭的時候如果發現要寫的那句 docblock 已經說過了，就把 docblock 裡的
那一句刪掉——留在下面的是背景，不是摘要。

寫法：說角度，不要複述檔名。

```ts
// 反例（等於沒寫）
// Tests for line-length.

// 正例
// 行寬規則本身：語言怎麼認、上限怎麼算、剩下的怎麼變成 margin。全部是純函式，
// 不碰版面——「算出來的值真的套到元素上」在 tests/browser/reader/line-length.spec.ts。
```

正例做到的事是**指出隔壁那一層在哪**。有了這一行，下一個想加測試的人才知道該加在哪邊，而不是
在手邊這一層再堆一條。

### 5. 不訂數量或時間上限，訂進場資格

沒有「瀏覽器層總共不超過 N 條」這種數字。上限會變成配額——快滿的時候開始擠，而擠掉的不見得是最沒
用的那條。

擋在前面的是上面那張表：**往上一層，門檻高一階。** 加一條之前先回答下層為什麼測不到，答不出來就
往下搬。

## 這幾種形狀直接刪

不用逐條想，看到就是候選：

1. **下層已經證明過的同一個命題，在上層第二次以後出現的。** 第一條算接線，之後的是副本。
2. **只斷言型別或欄位存在，不斷言值。** 例如
   [protocol.test.ts](../../packages/app/worker/mcp/protocol.test.ts) 的
   `gives every tool a name, a description and a schema`，那個 `for` 迴圈裡的三個
   `toBeTruthy()`——它擋不住任何一種真的會發生的錯，型別已經擋掉了。
3. **只斷言 mock 被呼叫過，不斷言呼叫造成的結果。** 「有叫到」不是使用者碰得到的東西。
4. **快照。** 這個 repo 目前一個都沒有，維持這樣。快照沒有命題，所以永遠回答不出「它測到什麼角度」，
   而更新它的動作是按一個鍵。
5. **混在功能測試裡順便驗平台或 library 行為的。** 該獨立就照原則 3 獨立，不該就刪。
6. **檔頭那一行寫不出來的整個檔。**

## 兩件這份文件不處理的事

**同一層裡兩個入口測同一段算術**，原則 1 管不到——它處理的是跨層。這種情況目前**留著**，因為兩個
入口本來就可能各有各的邊界要顧。真的只是同一件事換個函式名進去，那是重構的題目，不是刪測試的題目。

**刪掉一條測試會在 fixture 裡留下沒人用的東西**（沒人再引用的 id、只有那條測試會走到的分支）。
那些**留著不動**。清理它們要讀的是產品程式碼而不是測試，混在同一批改動裡會讓「刪掉的是不是真的副本」
變得看不出來。要清就另外開一次。

## frond：對照實作測試

frond 有一類測試在這份文件的框架下需要單獨講：把同一份輸入餵給 frond 與**對照實作**，斷言輸出一致
（`fflate`、`fast-xml-parser`、CFI 那邊的 foliate 驗收案例）。詞的定義在
[frond 的 CONTEXT.md](../../packages/frond/CONTEXT.md)。

它測到的角度別的層沒有：手寫預期值只能證明「我理解的規格」，而**對格式的誤解會讓預期值跟著一起錯**。
對照實作繞過這件事——答案來自另一套獨立寫成的程式。

兩個界線：

- **它不取代手寫的邊界測試。** 它只證明兩邊一致，不證明兩邊都對。已知的邊界情況還是要手寫。
- **能比的只有雙方都該同意的事實**——位元組、良不良構。錯誤訊息與資料形狀本來就該不同，比不得。

所以原則 1 對它不適用：對照實作測試跟手寫邊界測試不是同一個命題的兩份副本，它們測的是不同的角度。

## 加新測試的時候

一句話的流程：

1. 寫下這條測試的命題（「表意文字的行寬上限是 40em」）。
2. 問**最低哪一層證明得了它**，寫在那裡。
3. 如果上層也需要，問的是「接線通不通」，**只寫一條**。
4. 更新檔頭那一行。

## 掃過既有測試

準則訂下來之後要回頭掃一次，那件事有自己的 issue，處置預設是刪，每一條留一行理由。
掃完之後回到平常的節奏：**碰到哪個檔就順手看那個檔**，不做全 repo 的第二次普查。
